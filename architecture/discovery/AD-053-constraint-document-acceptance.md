# Constraint Document Atomic Acceptance

## 1. Gate-first and outcome

This act changes lifecycle authority but does not add or activate a rule, result or profile. It therefore is not positive-capable under OCP-016 G4. It supplies none of the consumer-baseline, rule-version, exact-input-snapshot, evaluation-context or legitimate-owner/evaluator bindings required for a positive activation. G4 does not apply to the lifecycle effect itself, and this act performs no activation.

All five AD-052 criteria applicable to `Draft → Accepted` are satisfied by the atomic package and its exact-head review lane; both Canonical-only criteria are explicitly inapplicable. OCP-006 therefore advances from `0.3.2 / Draft` to `0.4.0 / Accepted`. Constraint Concept status remains `Accepted`.

## 2. Criterion-by-criterion result

1. **Binding review lane — satisfied by the act and its external exact-head gates.** The proposal lives on a separate branch and draft PR. Its lifecycle effect exists only after exact-head Fable review, Codex adjudication, green required CI, explicit Architecture Board authorization and authorized squash merge. The repository cannot self-assert those external events; the witness labels this basis analytical and binds the governing text.
2. **Exact route and authority ledger — satisfied.** The witness names one route, every authority owner, all nine concrete Accepted consumers, the six exact direct dependencies, executable evidence, non-implications and migration/reopening effect.
3. **Board accepts current semantics — satisfied by this mandate and exact-head authorization.** Acceptance concerns the exact `0.3.2` reviewed body plus the readable lifecycle boundary in §30; it does not imply Concept canonicalization.
4. **Atomic document promotion unit — satisfied.** Version, status, compatibility surface, exact dependencies, reviewed snapshot, evidence, current gate projection and repository accounting change as one rollback unit.
5. **Canonical stability checks and separate Board act — not applicable.** The requested target is `Accepted`, not `Canonical`.
6. **Canonical direct-dependency L2 floor — not applicable.** It governs only `Canonical`; independently, OCP-005 remains Draft, so this act grants no Canonical implication.
7. **Exact-head authorization and atomic effect — satisfied only by the external gates and authorized squash.** Before merge the proposal has no lifecycle effect; after an authorized squash the entire unit takes effect together.

No criterion was inferred from open-question count or from the AD-050 discovery vocabulary. AD-052's criterion set is applied without reevaluation.

## 3. Route F, independently derived

Route F is selected from OCP-006's live subject, not copied from OCP-016's precedent guide. OCP-006 defines the registered Constraint identity, owns its lifecycle and supersession, specifies cross-foundation applicability/evaluation/admissibility semantics, and is projected through OCP-000 and OCP-002. That is a foundation Concept authority surface.

Route C is excluded because the document defines a registered identity rather than only a shared non-Concept contract. Route E is excluded because the authority is not merely a specialization of one other existing Concept. Route D is excluded because the semantics are foundation-wide rather than domain-local. Route I is excluded because no external system supplies the identity, lifecycle or evaluation authority. The OCP-016 precedent guide is recorded only as non-proof and performs no automatic reclassification.

The authority ledger is exact: Architecture Board owns the document semantics; OCP-000 owns the Concept registry; OCP-002 is the taxonomy projection; OCP-001 owns lifecycle rules; OCP-016 owns routing and activation boundaries; OCP-006@0.4.0 is the current semantic authority; and `reviewed-contract-v0.3.2.md` preserves the exact reviewed body.

## 4. Meaning of Accepted

Dependent specifications may build on exactly five existing surfaces:

- Constraint identity and supersession;
- structural lifecycle and temporal effectivity;
- the bounded applicability, evaluation-result and admissibility contract;
- fail-safe non-satisfaction and non-authorization/non-Conflict boundaries; and
- target-scope non-inheritance.

Acceptance grants lifecycle assurance for those already implemented semantics. It adds no field, rule, result, profile, transition, evaluator authority or runtime behavior.

The nine live Accepted direct consumers are OCP-011, OCP-013, OCP-014, OCP-015, OCP-017, OCP-018, OCP-019, OCP-020 and OCP-021. Each already depends on the unversioned `OCP-006` identifier. The executable ledger binds each consumer to the exact token and surface it consumes. For every one, the effect is `lifecycle-assurance-only`: data, schemas, references, evaluator ownership, derivations and negative boundaries are unchanged. No conditional positive behavior becomes legitimate.

Conversely, OCP-006 itself becomes one additional Accepted direct consumer of Draft OCP-005. The current consumer-need inventory is synchronized to include it. OCP-006's open and deferred Assignment references do not meet the three-part positive-need criterion: they do not state an exact new positive result without which OCP-006 cannot perform its present obligation. The existing unmet need remains only `RESOURCE_OCCUPANCY_ASSIGNMENT_SET_COMPLETENESS`; no other document's G4 answer changes.

## 5. Open surfaces remain outside the grant

Q1, Q2, Q6, Q7, Q8, Q10, Q11 and Q12 remain open. Respectively, dependents do not receive a Conflict object/aggregation, predicate language, dynamic-input currentness model, persistence mode, Operation authorization interaction, Readiness/availability handoff, kind taxonomy or domain relation language.

Q6 requires an explicit additional warning. AD-051 found that OCP-006's fail-safe rule presupposes a `current` authoritative evaluation but the norm defines neither a freshness magnitude, a currentness evaluator nor the instant at which dynamic-input evidence ceases to be current. Acceptance preserves the fail-safe result when its premise is met; it does not define the premise. No dependent may infer missing currentness semantics from `Accepted` status.

## 7. Version, migration and rollback

`0.3.2 → 0.4.0` is a pre-Canonical MINOR under OCP-001. The semantic body is unchanged, but lifecycle authority changes what dependent specifications are permitted to treat as an accepted foundation; that downstream admissibility effect is meaningful and is not editorial PATCH work. It is not MAJOR because no accepted contract is removed or made incompatible.

There is no data, reference, schema or runtime migration. Existing unversioned dependencies continue to resolve to OCP-006, and the nine consumers require no edit.

Rollback is one reviewed unit: restore `0.3.2 / Draft`, remove §30 and the current-accepted snapshot entry, restore the gate and accounting projections, and remove AD-053, its witness, historical succession data, checker and tests together. A partial rollback is invalid because it would separate status authority from its exact reviewed body, compatibility grant and evidence.

## 8. Non-implications

This act does not make OCP-006 Canonical; close any question; activate a positive model; change any Concept or Concept status; select a candidate; start a promotion cycle; authorize a next act; modify OCP-005; modify OCP-016; rewrite AD-052; or promote another document. The Event cycle remains the only completed cycle and `active_cycle_id` remains null. Any later canonicalization, candidate selection or cycle start requires a separate mandate and new exact-head gates.
